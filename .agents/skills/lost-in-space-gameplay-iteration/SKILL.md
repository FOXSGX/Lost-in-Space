# 迷失太空玩法迭代 Skill

这是一套“设计 → 现实校验 → Godot 验证 → 反馈归档 → 下一轮设计”的项目工作流。它服务于当前 Godot 4 本地 3D 联机项目，不把项目改造成浏览器游戏，也不把美术制作当作玩法迭代的前置条件。

## 设计真源与状态标记

开始前读取：

1. `AGENTS.md`
2. `README.md`
3. `docs/design/游戏设计总纲.md`
4. 当前星球设计文档
5. 对应的 `game/docs/` 玩法说明
6. 对应的 `game/tests/` 测试脚本

所有输出都要把内容标记为以下之一：

- `已确认方向`：用户或团队已经确认的规则；只能解释和验证，不能擅自反向修改。
- `团队倾向`：已有倾向但未锁定的方向；可以作为约束候选。
- `待讨论建议`：本轮新产生的候选，不得写入设计总纲或星球正式文档。
- `观察事实`：来自测试日志、截图、代码或试玩记录的事实。
- `设计假设`：尚未通过玩家行为或运行证据验证的推断。

## 外部设计 Skill 的协同

如果以下 Skill 已安装，按任务调用；没有安装时，使用本 Skill 的同等阶段完成工作：

- `$gamestudio`：跨职能游戏设计流程、玩法支柱、关卡、任务、叙事、UX 和验收门槛。
- `$gameplay-mechanism-designer`：把种子想法展开为多个机制方向、循环、系统关系和最小原型。
- `$game-design-reality-check`：把“应该好玩”改写为可证伪假设，寻找最便宜的验证试玩。

调用外部 Skill 时，明确告诉它读取当前项目文档，并保持 Godot 4、1—4 人联机、主机权威和现有星球接口；不要让它重选引擎或套用浏览器游戏实现方案。

## 每轮固定阶段

### A. 建立上下文快照

创建 `work/gameplay-iterations/<iteration-id>/`，保存：

- 迭代目标和范围；
- 读取过的设计文档清单；
- 相关文件的 SHA-256；
- 当前测试入口；
- 本轮禁止修改的文件和规则。

### B. 设计发散

先写 `02-design-options.md`，至少给出两个结构不同的方案。每个方案必须说明：

- 玩家目标和体验目标；
- 玩家反复做的动作和决定；
- 规则、状态、资源、反馈和失败恢复；
- 多人职责、单人替代和中途加入/掉线影响；
- 与当前地图、剧情和长期探索系统的关系；
- 最小可玩验证范围；
- 明确的非目标，防止扩大项目规模。

### C. 现实校验

写 `03-reality-check.md`，把重要结论分为观察事实、设计推导、设计假设和未知。至少检查：

- 玩家是否能理解目标和阻挡原因；
- 是否存在一个明显的最优解；
- 机制是否真的改变玩家决定，而不是只增加内容；
- 叙事是否由玩家行为触发，而不是脱离玩法的说明文本；
- 多人和单人的体验是否都能完成；
- 失败后是否知道原因并愿意重试；
- 是否有最小成本的决定性试玩。

### D. Godot 验证计划

写 `04-test-plan.md`，为每个设计假设指定：测试入口、操作步骤、观察信号、通过条件、失败条件和对应的设计决定。优先使用已有测试，不为镜像实现新增无意义测试。

可用测试入口包括：

- `res://tests/resonance_stage.gd`
- `res://tests/resonance_runtime.gd`
- `res://tests/ship_hub_integration.gd`
- `res://tests/ship_hub_network.gd`
- `res://tests/story_arc.gd`
- `res://tests/campaign_systems.gd`
- `res://tests/exploration_features.gd`
- `res://tests/reachability.gd`
- `res://tests/field_interactions.gd`
- `res://tests/capture_view.gd`
- `res://tests/resonance_scene_diagnostic.gd`：只读检查敌人场景资源、脚本常量和主机测试状态。
- `res://tests/resonance_spawn_isolation.gd`：隔离复现共振星阶段安保生成，不混入其他玩法操作。
- `res://tests/iteration_planet_capture.gd`：在不覆盖原稿的前提下记录两颗星球的 HUD、目标、日志和交互截图。
- `res://tests/iteration_network_smoke.gd`：用两个真实 Godot 进程验证主舱、霜烬星和共振星往返同步。
- `res://tests/ship_hub_persistence_diagnostic.gd`：隔离验证主舱 `user://` 存档写入和读取。

运行 `tools/gameplay-iteration.ps1` 生成可追溯日志，不把测试通过等同于玩法已经有趣。

完整检查入口为 `-Suite full`；视觉捕获可以单独用 `-Suite visual`，完整套件使用迭代目录专用输出副本，避免覆盖现有美术原稿。

### E. 运行与反馈归档

测试结果写入 `05-test-report.md`，至少包含：

- 运行时间、Godot 版本、测试套件；
- 每项测试的退出码和摘要；
- 观察事实与错误日志；
- 玩法、叙事、交互、地图和探索层面的影响；
- 未覆盖的风险；
- 下一轮要验证的一个最小假设。

编排器会把 Godot 的解析/加载错误、空 `PackedScene` 实例化错误和显式 `*_FAILED` 标记视为失败，即使 Godot 进程错误地返回 0；因此不能只看退出码。

用户试玩反馈写入 `06-feedback.md`，保留原话并标记来源。不要直接把用户提出的修改方案当作决定。

### F. 迭代门槛

一轮结束时只允许输出以下三种结果：

- `继续设计`：测试暴露了新的关键未知，需要下一轮方案或更小原型。
- `准备申请修改`：设计方向和验证证据足够，列出将改哪些文件，但不自动修改。
- `暂不修改`：问题主要是美术、性能、网络基础设施或信息不足，交给对应负责人或补充证据。

只有用户明确批准后，才可以进入代码或正式设计文档修改。修改后必须重新运行受影响的 Godot 测试，并更新迭代记录。

## 本项目的首轮使用方式

当前只搭建工作流，不修改共振星或霜烬星。后续首轮设计输入应把已有试玩反馈作为 `观察事实/待讨论建议` 读取，优先验证“流程阻塞是否真实存在、玩家是否理解阻挡原因、双人和单人的核心目标是否清晰”，而不是直接执行反馈中的修复清单。
