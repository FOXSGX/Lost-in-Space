## 1. 滑槽：真实根因（台架实测）

台架 `mech001b_chute_bench`（货台 1.35 / 导轨 0.84 / 挡块，60 kg 模块，530 N 受限牵引）:

### 1.1 修复前
```
chute_basis_x=(1.0, 0.0, 0.0)  y=(0.0, -0.358, -0.934)  z=(0.0, 0.934, -0.358)
size=(1.45, 1.52443, 0.1)
模块 t=0..419 全部 pos=(0.00,1.85,0.00) v=0.00     ← 完全没动
```
`basis.y` 指向 **下前方**（坡面法线朝下）、`basis.z` 指向 **上后方向**。
也就是说：`Quaternion(UP, dir)` 把**厚度轴 Y 转成了行进方向**，那块 `1.45×1.52×0.10` 的板
**立成一片竖鳍**，模块只是被它挡了一下或被别的支撑托着，根本没有"沿坡面下滑"这回事。

> 上一份报告猜"法线反向导致穿透"——**方向猜对了，但机制说错了**：不是穿透，是板子装反了朝向。

### 1.2 修复后（正交基：Y=法线、Z=行进、X=宽度）
```
chute_basis_x=(-1.0,0,0)  y=(0.0, 0.934, -0.358)  z=(0.0, -0.358, -0.934)   size=(1.45,0.1,1.56443)
peak=2.63 m/s   final=(0.01, 1.33, -3.04)   stop_z=-3.62（挡块面 -3.56）
```
模块**沿坡面滑下、落到导轨面（1.33 ≈ 0.84+0.51）并在挡块前停住**（前缘 -3.55 ≈ 挡块面 -3.56）。

修复代码（WIP 中已存在）：
```gdscript
func _ramp_basis(seg: Vector3) -> Basis:
    var z_ax := seg.normalized()
    var n := z_ax.cross(Vector3.RIGHT).normalized()
    if n.y < 0.0: n = -n
    return Basis(n.cross(z_ax).normalized(), n, z_ax)
```
并把板子尺寸改为 `Vector3(1.45, 0.10, seg_len + 0.14)`（厚度在 Y、长度在 Z）。

## 2. 夹爪：已定位一半

### 2.1 已修：铰链轴朝向
台架 `mech001b_clamp_bench` 第一版打印：
```
axis=(1.0, 0.0, 0.0)     ← 世界 X（水平），夹爪绕 X 倒下去；而我读的是 rotation.y → 永远 0
```
这解释了第一幕里 `clamp_angle = 0.00`：**不是电机没劲，是关节轴装错了。**
把关节改成 `Basis(Z, PI/2)`（局部 X → 世界 Y）后：
```
axis=(0.0, 1.0, 0.0)     ← 正确
```

### 2.2 未修：夹爪仍完全不响应力矩
轴向正确后，电机目标速度 1.25、`MAX_IMPULSE=200`，夹爪依旧 `angle=0.000 w_y=0.000`。
进一步诊断：**直接施加 60 N·m·s 角冲量**：
```
diag freeze=false sleeping=false inv_inertia_diag=(1.000,1.000,1.000) w_after_impulse=0.000
```
刚体既不冻结也不休眠，但角冲量产生的角速度为 0，且逆惯量张量读数是默认值。
因此问题**不在马达冲量大小**（任务也明确禁止先调这个参数），而在更底层：
关节进入树后的绑定形式、Jolt 下 Hinge + LIMIT 的锁死行为、或该刚体的惯量未被正确计算。
这三条都还没有被证伪，需要下一轮继续用台架二分。

## 3. 为什么没有把台架修复搬进正式关卡（以及为什么失败）

我按顺序做了：WIP 恢复 → 应用 `_ramp_basis` → 夹爪退回 001A 的可用行为（E 置 flag）→ 跑 001A 专项。

结果：
```
X3 FAIL  最小位移 7.95 m，最大插座误差 2.05 m，峰值 5.03 m/s
X4 FAIL  末轮 flag=false
X5 FAIL  距起点 0.070 m
```
**与修复前的数字逐位相同**（7.95 / 2.05 / 5.03）。这说明第一幕里模块走的**根本不是台架那条路径**，
`_ramp_basis` 的修复在正式关卡里没有生效或没有作用到模块上。可能的具体差异（未逐一验证）：

1. 模块初始在**推车货台**上（act1 里 `cart * (0,1.92,0)`，底面 1.41），而台架是直接放在货台面；
   模块可能先在车台上被牵引力拖离边缘、**从滑槽侧面掉下去**，根本没接触坡面；
2. act1 的滑槽起止点用的是 `cart.global_position.y + 1.37`，而台架用的是绝对 1.35；
3. act1 的牵引是 `_drive_winch()` 里对 `module_target` 的持续力，方向是**指向插座**，
   而台架是固定 -Z；两者在模块离开车台后受力方向差别很大。

**结论**：集成失败的原因是"模块在 act1 里的起点与受力路径和台架不同"，
不是滑槽几何本身——滑槽几何的修复本身是有台架证据的。
